Scaffolding Ladder Scope

Every lesson in this course is meant to ask the same three questions out loud — what are the parts, where do I read about each one, how is this like something I already built. Forty-six of the eighty-one now do. This is what is left, and the case for leaving most of it alone.

46 On the ladder
35 Not on it
0 Defects found

The recommendation

Leave the remaining 35 off the ladder — with one judgment call.

Thirty-three of them are not lessons that teach a build. They are studio days, jam days, CPT work days, exam practice, and two setup days. The block decomposes a problem the student is about to solve in code, and a day spent working on a project already in flight has no such problem to split.

The exception is 7.5 8.1, the two design days. Those already are decompositions — 8.1's Six-Part Spec and 7.5's four-step Paper Cave are decompositions written in prose. Adding the block there buys no new pedagogy, only a consistent frame and captured answers. That is a real but small win, and the one call worth making deliberately.

Where the ladder sits

The rungs are per-concept, not per-week: the first time a student meets a shape they are walked through it, and every later appearance of the same shape gets less. So the count is not a progress bar — a rung 4 lesson early in a unit can be harder than a rung 2 lesson later on.

1 Full walkthrough Every line given and explained. A mechanism with no precedent in the course. 9 lessons
2 Guided build A known shape carrying exactly one new idea, and that idea is the gap the student fills. 9 lessons
3 Outline only Parts named and sourced; what each one does is the student's to say. No code scaffold at all. 26 lessons
4 Solo build The same parts in a new arrangement. Nothing new at all — even the splitting is theirs. 2 lessons

Rung 3 carries the most lessons by a wide margin, and that is the design working as intended. Once the whole Unit 9 concept sequence and the Unit 10 card lessons are counted, "name the parts, point at the reading, withhold the reasoning" is simply what a lesson looks like in the back half of the course.

Why the pass was worth running

The block was the excuse; the ground truth was the point. Every lesson rolled onto the ladder had its project claims checked against the actual Unity project, and several were wrong in ways no amount of proofreading would have caught.

9.8 Taught sudo dscacheutil -flushcache as a DNS cache flush. It has not flushed the macOS resolver since 10.14 — the student would have watched nothing happen. Replaced with an nslookup demonstration that needs no sudo and is true on every platform.
9.8 Called the project "2 MB" and a scene "~1,500 chunks". The Assets folder is 20,185,356 bytes and the scene is 1,629 packets. That tenfold error is why every packet number in the lesson was recomputed from real file sizes.
7.2 Taught the layer-mask trap backwards: that the mask "defaulted to everything" and widened the physics queries. In fact LayerMask.GetMask("Ground") in a project with no Ground layer returns an empty mask — so the ground check reads false forever and the player jumps in mid-air. The opposite failure from the one being taught, with the opposite fix.
8.3 Claimed "this project has no custom physics layers yet" — false by Unit 8, since 7.2 has the student create Ground, Player, Enemy, Projectile and Decoration. It also described the quick reference as covering Physics2D queries and layer masks; it covers neither.
10.2c
10.2d Handed the student C# that would not compile. A bare Random.Range in GameManager.cs is CS0104 — the file has both using Unity.Mathematics and using UnityEngine, and the mathematics package declares its own Random. Now fully qualified, and the ambiguity is kept as a teaching moment in both lessons.
10.2b A whole Build Lab step told students to add [SerializeField] private List<Card> startingDeck; to the game manager. No such field exists — the deck is player_deck, already authored in the Inspector. The lesson also credited a [SerializeField] reference to 3.1 that 3.1 does not contain.
10.2d The whole AI was fiction: aiHand, aiEnergy, c.attack, c.defense, PlayCard(), Pass(), EndTurn() — none of which appear anywhere in the project. It handed over a complete solution that would not have run. Rewritten onto the real names (ai_hand, ai_discard_pile, Card.cost/.damage/.health).

8.2 All three asserted that no prefab in the project carries a collider. One does — Switch.prefab, a trigger BoxCollider2D with no body behind it, whose script has no physics callback at all. The overstatement started in 2.1 and propagated into two later lessons before it was caught.
9.10 The license claim was the risky one, and it held: AP_CS_P_Starter_Project/LICENSE is Apache 2.0, 201 lines, not MIT. Worth recording that the Unit 10 card template ships no LICENSE file at all — so license steps must say "your fork's repo" and never point at a path in the course repo.

Verification

Every lesson was checked by replaying the site verifier's ladder rules statically: extracting the real frontmatter, rendering it through the actual walkthrough, decompose and formify modules, and asserting the same conditions the build asserts — level agreement between the banner, the walkthrough, the block and the index; docs === parts; the per-rung decay; a non-empty prompt behind every answer box; and no reference in the connect beat to a lesson the student has not reached yet.

The full gate was then run for real: npm run build and npm run verify, which pass — 115 pages, 2585 links, 81 lessons, 46 carrying the block. The sweep found zero defects in any lesson already on the ladder. Two control lessons that predate the rollout — 4.3 at rung 4 and 6.2 at rung 2 — pass the same rules, which is what says the checker agrees with the shipped site rather than with itself.

Saved answers were preserved exactly. The harvested blocks (bug-hunt, tinker, socratic) carry positional ids, so every item was reworded in place and none was reordered, renumbered, added or removed. The decompose block opens a new answer namespace on each lesson rather than displacing an existing one.
